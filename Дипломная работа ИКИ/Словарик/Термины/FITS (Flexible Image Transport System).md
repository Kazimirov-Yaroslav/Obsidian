# FITS (Flexible Image Transport System)

**FITS** — стандартный формат хранения и обмена научными данными в астрономии. Это не «формат картинок», а контейнер, который хранит **данные вместе с полным описанием того, как их понимать**: метаданные наблюдения, калибровку, физические единицы, систему координат.

> [!abstract] Коротко
> FITS-файл — это последовательность блоков **HDU (Header Data Unit)**. Каждый блок состоит из:
> - **Header** — человекочитаемые метаданные в ASCII (карточки по 80 символов);
> - **Data** — бинарные данные (изображение, таблица или ничего).
>
> Ключевая философия формата: **данные без описания бессмысленны**. Поэтому заголовок несёт всю информацию, нужную для превращения байтов в физические величины: тип данных, размерности, единицы, дату и инструмент наблюдения, координатную привязку.
>
> Для диплома FITS важен как источник исходных солнечных изображений: серии SOHO MDI (`continuum` + магнитограмма) приходят именно в этом формате, причём в tile-сжатом виде.

## История и стандарт

FITS разработан в конце 1970-х для обмена данными между обсерваториями и официально стандартизирован Международным астрономическим союзом. Действующая версия стандарта — **4.0 (август 2018)**; формальное определение формата опубликовано в статье Pence et al. (2010) в Astronomy & Astrophysics.

> [!note] Долголетие как свойство стандарта
> FITS служит астрономии более 40 лет. Принцип «once FITS, always FITS»: файлы, записанные десятилетия назад, обязаны читаться современным ПО. Обратная сторона — консервативность: формат не меняют ради модных фич, а расширения добавляют через строгие конвенции (например, tile-сжатие).

Формат поддерживается NASA FITS Support Office, которая ведёт стандарт, реестр конвенций и документацию.

## Структура FITS-файла

### Header Data Unit (HDU)

Файл состоит из одной или нескольких **HDU**. Первая называется **Primary HDU** (`HDU[0]`) и обязательна; остальные — **расширения** (`HDU[1]`, `HDU[2]`, …).

![[fits_primary.png]]

На схеме видно устройство Primary HDU: последовательность **синих блоков заголовка** (Header, ASCII-карточки) и, опционально, **красных блоков данных** (Data, бинарные). Вместе они образуют один Header Data Unit. Надпись «continues below» означает, что файл может продолжаться следующими HDU.

> [!note] Что важно запомнить из схемы
> - Заголовок **обязателен**, данные — **опциональны**: HDU может состоять только из метаданных.
> - Заголовок человекочитаем (ASCII), данные — бинарны; вся информация о том, как расшифровать байты данных, лежит в заголовке.
> - Блоков заголовка может быть много: он разбит на фиксированные порции по 2880 байт.

### Заголовок: карточки keyword

Заголовок состоит из записей фиксированной длины **80 символов** вида:

```text
KEYWORD = значение / комментарий
```

Пример реального заголовка солнечного наблюдения:

```text
SIMPLE  =                    T / conforms to FITS standard
BITPIX  =                  -32 / array data type (float32)
NAXIS   =                    2 / number of array dimensions
NAXIS1  =                 1024 / width
NAXIS2  =                 1024 / height
DATE-OBS= '2005-01-01T00:00:00' / observation date
TELESCOP= 'SOHO'               / telescope name
INSTRUME= 'MDI'                / instrument name
BUNIT   = 'I/I_QS'             / brightness units
```

Ключевые карточки:

| Keyword | Смысл |
|---|---|
| `SIMPLE` | Соответствие стандарту FITS |
| `BITPIX` | Тип данных массива (см. таблицу ниже) |
| `NAXIS`, `NAXISn` | Число осей и размеры массива |
| `BUNIT` | Физические единицы значений пикселей |
| `DATE-OBS` | Дата и время наблюдения |
| `TELESCOP`, `INSTRUME`, `OBSRVTRY` | Источник данных |
| `CRPIX`, `CRVAL`, `CDELT`, `CTYPE` | WCS-координаты (см. ниже) |
| `HISTORY`, `COMMENT` | История обработки и свободные комментарии |

> [!warning] Заголовок — контракт, а не пожелание
> Отсутствие или некорректность ключевых карточек ломает downstream-обработку. Известный пример из практики диплома: в магнитограммах MDI отсутствует `BUNIT`, и единицы (гауссы) пришлось подтверждать косвенно — по диапазону значений ±(1000–3000) Гс и биполярности структуры. Подробнее — в [[Анализ данных]].

### Расширения: Multi-Extension FITS

После Primary HDU в файле может следовать произвольное число расширений, каждое со своим заголовком и данными.

![[fits_extension.png]]

На схеме показан файл с расширениями: `Extension 1` (`HDU[1]`) … `Extension N` (`HDU[N]`), каждое повторяет структуру «заголовок + данные». Типичная организация: **Primary HDU содержит только общий заголовок**, а сами данные лежат в расширениях.

> [!note] Зачем это нужно в солнечных данных
> MEF позволяет хранить связанные продукты наблюдения в одном файле: например, пару «континуум + магнитограмма» или серию кадров во времени. В серии MDI `mdi.fd_Ic_interp_96m` каждому моменту времени соответствует пара файлов `.continuum` (видимый свет) и `.data` (LOS-магнитограмма).

Типы расширений:

| Тип | Содержание |
|---|---|
| `IMAGE` | Многомерный массив (изображение, куб) |
| `BINTABLE` | Бинарная таблица (каталог, спектр) |
| `TABLE` | ASCII-таблица (устаревший вариант) |

### Типы данных и BITPIX

Карточка `BITPIX` задаёт тип элемента массива:

| BITPIX | Тип | NumPy dtype |
|---|---|---|
| 8 | unsigned byte | `uint8` |
| 16 | 16-bit целое со знаком | `int16` |
| 32 | 32-bit целое со знаком | `int32` |
| -32 | 32-bit вещественное | `float32` |
| -64 | 64-bit вещественное | `float64` |

> [!info] Из практики диплома
> В паре MDI: `continuum` хранится как `float32`, магнитограмма — как `float64`. Разная точность отражает разную природу величин: нормированная интенсивность против поля в гауссах.

### Выравнивание по 2880 байт

Каждый заголовок и каждый блок данных дополняются до размера, кратного **2880 байтам** (исторический размер блока магнитной ленты). Поэтому размер любого корректного FITS-файла кратен 2880 - дополняться может просто пробелами (после блока с заголовками) или нулями (после блока с данными), без информации.

## Tile-compressed FITS и алгоритм RICE

### Зачем сжимать плитками

Солнечные архивы огромны: даже одна серия MDI с каденсом 96 минут даёт ~5139 кадров в год по 1024×1024, то есть порядка 13 ГБ в год на пару продуктов. Прямое gzip-сжатие всего файла решило бы проблему объёма, но убило бы **произвольный доступ**: чтобы прочитать один кадр или область, пришлось бы распаковывать всё.

**Tile-compressed FITS** решает обе задачи: изображение делится на прямоугольные **плитки**, каждая плитка сжимается **независимо** и хранится как отдельная строка бинарной таблицы. Чтобы прочитать область изображения, достаточно распаковать только пересекающиеся плитки.

### Как устроен tile-compressed FITS

Сжатое изображение хранится не как `IMAGE`-расширение, а как **бинарная таблица**, которая по конвенции интерпретируется читателями (cfitsio, astropy, DS9) как изображение:

- каждая **строка таблицы** = одна сжатая плитка;
- колонка `COMPRESSED_DATA` содержит байты сжатых плиток;
- колонка `UNCOMPRESSED_DATA` хранит плитки, которые не удалось сжать (например, содержащие NaN);
- заголовок расширения несёт служебные карточки конвенции:

| Keyword | Смысл |
|---|---|
| `ZCMPTYPE` | Алгоритм сжатия (`RICE_1`, `GZIP_1`, `HCOMPRESS_1`, …) |
| `ZBITPIX`, `ZNAXISn` | Тип и размерность **исходного** изображения |
| `ZTILEn` | Размер плитки |
| `ZNAME1 = 'BLOCKSIZE'`, `ZVAL1` | Параметр алгоритма RICE (размер блока, обычно 32) |
| `ZSCALE`, `ZZERO` | Масштаб и смещение квантования float → int |
| `ZQUANTIZ` | Метод дитеринга при квантовании |



![[tile_rice_pipeline.svg]]

Схема показывает tile-сжатие как двусторонний процесс: верхняя половина — путь одной плитки от пикселей до строки таблицы `COMPRESSED_DATA`, нижняя — обратный путь от строки обратно на своё место в кадре. Голубым в обеих сетках выделена **одна и та же плитка** (идентичная клетка сверху и снизу), поэтому два потока читаются как зеркало друг друга; остальные плитки нейтральные — они сжимаются независимо, и их содержимое на схеме не раскрывается.

> [!tip] Прозрачность для пользователя
> Astropy и cfitsio распаковывают такие файлы автоматически: `hdul[1].data` возвращает обычное изображение, а `hdul.info()` показывает расширение как изображение, а не как таблицу. Поэтому tile-сжатие легко «проглядеть»: файл выглядит как обычный FITS. В мини-работе по маске этот вопрос закрыт именно так: формат серии MDI — tile-compressed FITS.

### Алгоритм RICE (RICE_1)

**RICE_1** — реализация в FITS алгоритма Райса (R. Rice, JPL), разработанного для сжатия телеметрии и ставшего де-факто стандартом сжатия астрономических изображений.

**Математическая основа — коды Голомба–Райса.** Целое значение $x \geq 0$ кодируется парой $(q, r)$:

$$
x = q \cdot 2^k + r, \quad 0 \le r < 2^k
$$

- частное $q$ кодируется унарно ($q$ единиц и ноль);
- остаток $r$ — двоичным кодом из $k$ бит.

Параметр $k$ подбирается **адаптивно для каждого блока** из его статистики, поэтому код близок к оптимальному для распределений с «тяжёлым хвостом» малых значений (каковы разности соседних пикселей гладких полей).

**Пайплайн сжатия плитки:**

1. Знаковые значения отображаются в беззнаковые «складыванием»: $0, -1, 1, -2, 2, \ldots$
2. Блок из `BLOCKSIZE` значений (по умолчанию 32) кодируется адаптивным кодом Голомба–Райса.
3. Для каждого блока выбирается лучший из нескольких вариантов кодирования, включая «без сжатия».

**Точность:**

- Для **целочисленных** данных RICE_1 **строго обратим** (lossless).
- Для **вещественных** данных (`float32`/`float64`) сначала применяется **квантование**: значения масштабируются карточками `ZSCALE`/`ZZERO` и округляются до целых. Этот шаг **необратим**, но контролируем: уровень квантования задаёт, какая доля шума сохраняется в младшем бите, а дитеринг (`ZQUANTIZ`) убирает систематическое смещение. Далее целые сжимаются обратимо.
- Итог: «RICE для float = управляемо-lossy квантование + lossless кодирование». Для научных задач квантование обычно выбирают так, чтобы потери были много ниже уровня шума прибора.

**Почему RICE популярен в астрономии:**

> [!success] Преимущества
> - Очень быстрый (простые битовые операции), подходит для конвейеров.
> - Хорошая степень сжатия на гладких полях с шумом: типично 2–4× для солнечных изображений.
> - Поблочно-адаптивный: не требует знания статистики всего изображения.
> - Плиточная упаковка даёт произвольный доступ и устойчивость: повреждение одной плитки не убивает весь кадр.

> [!example]- Числовой пример: как код Голомба–Райса кодирует блок
>
> Возьмём блок из 8 целых неотрицательных значений (в реальном RICE_1 `BLOCKSIZE = 32`, здесь меньше для наглядности):
>
> $$X = [3,\; 7,\; 1,\; 5,\; 12,\; 2,\; 4,\; 8]$$
>
> **Шаг 1. Выбор $k$.** Параметр подбирается по статистике блока, ориентировочно $k \approx \lfloor \log_2 \bar{X} \rfloor$. Здесь $\bar{X} = 42/8 = 5.25$, поэтому $k = 2$ (то есть $2^k = 4$).
>
> **Шаг 2. Разложение значений.** Каждое значение раскладывается как
>
> $$x = q \cdot 2^k + r, \quad q = \lfloor x / 2^k \rfloor, \quad r = x \bmod 2^k$$
>
> после чего $q$ кодируется унарно ($q$ единиц и завершающий ноль), а $r$ — двоично ровно $k$ битами:
>
> | $x$ | $q$ | $r$ | Унарный $q$ | Двоичный $r$ ($k=2$) | Код | Бит |
> |---|---|---|---|---|---|---|
> | 3 | 0 | 3 | `0` | `11` | `0 11` | 3 |
> | 7 | 1 | 3 | `10` | `11` | `10 11` | 4 |
> | 1 | 0 | 1 | `0` | `01` | `0 01` | 3 |
> | 5 | 1 | 1 | `10` | `01` | `10 01` | 4 |
> | 12 | 3 | 0 | `1110` | `00` | `1110 00` | 6 |
> | 2 | 0 | 2 | `0` | `10` | `0 10` | 3 |
> | 4 | 1 | 0 | `10` | `00` | `10 00` | 4 |
> | 8 | 2 | 0 | `110` | `00` | `110 00` | 5 |
>
> **Шаг 3. Итоговый битовый поток блока:**
>
> ```text
> 011 1011 001 1001 111000 010 1000 11000
> ```
>
> Это **32 бита** против $8 \times 16 = 128$ бит при хранении тех же значений 16-битными целыми: сжатие в 4 раза на этом блоке.
>
> **Шаг 4. Декодирование (на коде `1110 00`).** Читаем унарную часть: три единицы и ноль → $q = 3$. Читаем следующие $k = 2$ бита: `00` → $r = 0$. Восстанавливаем $x = q \cdot 2^k + r = 3 \cdot 4 + 0 = 12$. ✓
>
> **Складывание знаков.** Код Голомба–Райса определён только для неотрицательных целых, поэтому знаковые значения сначала отображаются в беззнаковые:
>
> $$f(x) = \begin{cases} 2x, & x \ge 0 \\ -2x - 1, & x < 0 \end{cases} \qquad f^{-1}(u) = \begin{cases} u/2, & u \text{ чётное} \\ -(u+1)/2, & u \text{ нечётное} \end{cases}$$
>
> | Исходное | 0 | -1 | +1 | -2 | +2 | -3 | +3 |
> |---|---|---|---|---|---|---|---|
> | Сложенное | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
>
> Для вещественных пикселей перед этим идёт квантование до целых через `ZSCALE` / `ZZERO` (и дитеринг `ZQUANTIZ`); обратное преобразование $x_{\text{float}} = \text{ZSCALE} \cdot x_{\text{int}} + \text{ZZERO}$ восстанавливает физические значения.
>
> **Что хранится помимо самих байт:** выбранный $k$ для блока (обычно байт на блок), маркер «плитка/блок не сжат» для случаев, когда сжатие невыгодно (например, плитки с NaN), и параметры квантования для float-данных.

> [!note] Почему адаптивность критична
> При фиксированном $k$ код неэффективен: слишком малое $k$ раздувает унарные части, слишком большое — двоичные. RICE выбирает $k$ отдельно для каждого блока, поэтому одинаково хорошо сжимает и гладкие участки (малые значения → малый $k$) и области с яркими деталями (крупные значения → больший $k$).

### Другие алгоритмы сжатия в конвенции

| Алгоритм | Свойства | Когда используют |
|---|---|---|
| `RICE_1` | Быстрый, обратимый для целых | Основной выбор для изображений |
| `GZIP_1` | Универсальный gzip по плиткам | Когда RICE не даёт выигрыша |
| `GZIP_2` | gzip с перестановкой байтов | Лучше для float-данных |
| `PLIO_1` | Список пикселей (IRAF) | Маски, разреженные данные |
| `HCOMPRESS_1` | Иерархический, с потерями | Превью, визуализация |
| `NOCOMPRESS` | Хранение как есть | Плитки с NaN и особые случаи |

### Чтение и запись в astropy

```python
from astropy.io import fits

# Чтение: распаковка прозрачна
with fits.open('mdi_continuum.fits') as hdul:
    hdul.info()          # расширение выглядит как изображение
    data = hdul[1].data  # уже распакованный массив 1024x1024

# Запись в tile-сжатом виде
hdu = fits.CompImageHDU(data=data, compression_type='RICE_1')
hdu.writeto('compressed.fits', overwrite=True)
```

> [!note]+ Построчный разбор
> 1. `fits.open(...)` — открывает файл лениво: байты плиток не читаются до обращения к `.data`.
> 2. `hdul.info()` — для tile-сжатого файла покажет расширение как изображение, а не как бинарную таблицу.
> 3. `hdul[1].data` — astropy сама находит колонку `COMPRESSED_DATA` и распаковывает нужные плитки.
> 4. `fits.CompImageHDU(...)` — создаёт расширение по конвенции tile-сжатия; `compression_type='RICE_1'` выбирает алгоритм Райса.

## WCS: координаты в заголовке

WCS (World Coordinate System) — набор карточек, связывающих пиксели с физическими координатами на небе или на Солнце:

- `CRPIX1/2` — опорный пиксель (для солнечных данных обычно центр диска);
- `CRVAL1/2`, `CTYPE1/2` — координаты опорного пикселя и тип системы;
- `CDELT1/2` или `CDi_j` — масштаб пикселя (например, в угловых секундах);
- для Солнца дополнительно: гелиографические координаты наблюдателя, радиус Солнца в пикселях, угол вращения.

Благодаря WCS одна и та же маска или пятно могут быть сопоставлены между инструментами и датами — это основа кросс-инструментальных сравнений в дипломе.

## Специфика солнечных данных (на примере SOHO MDI)

Задокументированные особенности рабочей серии `mdi.fd_Ic_interp_96m` (2005 год, каденс 96 минут, 5139 пар кадров, 1024×1024):

> [!info] Инвентаризация данных
> - **Формат:** tile-compressed FITS; расширение `.fits` в проводнике может быть скрыто.
> - **Пара продуктов:** `.continuum` (видимый свет, уже CLV-скорректирован и нормирован на Quiet Sun, `float32`) и `.data` (LOS-магнитограмма, `float64`).
> - **BUNIT магнитограммы отсутствует;** единицы (гауссы) подтверждены косвенно диапазоном ±(1000–3000) Гс и биполярностью.
> - **QC-флаги:** кадры с флагами `flat` и `dip` (ровно два: 20050614_160000 и 20050615_080000) исключаются из всех сплитов.
> - **Epoch-дрейф порога umbra:** январь против июля–декабря даёт сдвиг ≈0.10–0.15 по нормированной интенсивности; лечение (CLV-фит по радиусу) отложено до версии v1 генератора масок.

Эти особенности — свойства конкретного архива, которые напрямую влияют на генерацию масок (см. [[Генератор масок]]) и инженерные ограничения ([[M0-02 Инженерная среда и ограничения железа]]).

## Практика в Python (astropy)

### Базовые операции

```python
from astropy.io import fits

with fits.open('solar_image.fits') as hdul:
    hdul.info()                 # структура файла
    header = hdul[0].header     # заголовок Primary HDU
    data = hdul[0].data         # данные как NumPy-массив
    mag = hdul['MAG'].data      # доступ к расширению по имени
```

> [!note]+ Построчный разбор
> 1. `fits.open(...)` в контекстном менеджере гарантирует закрытие файла.
> 2. `hdul.info()` печатает таблицу HDU: тип, размерность, тип данных — первый шаг при знакомстве с любым FITS.
> 3. `hdul[0].data` возвращает NumPy-массив; для tile-сжатых файлов распаковка происходит прозрачно.
> 4. Обращение по имени расширения (`'MAG'`) читается лучше, чем по индексу.

### Чтение и проверка карточек

```python
date_obs = header['DATE-OBS']
bunit = header.get('BUNIT', None)   # None, если карточки нет

if bunit is None:
    # единицы неизвестны: фиксировать как известный недостаток данных
    ...
```

> [!warning] Правило работы с чужими заголовками
> Всегда использовать `.get()` с значением по умолчанию для необязательных карточек: их отсутствие — норма для реальных архивов, а не исключительная ситуация.

### Запись и MEF

```python
primary = fits.PrimaryHDU()                      # только общий заголовок
cont = fits.ImageHDU(data=continuum, name='CONTINUUM')
mag = fits.ImageHDU(data=magnetogram, name='MAGNETOGRAM')

fits.HDUList([primary, cont, mag]).writeto('obs.fits', overwrite=True)
```

## Сравнение с другими форматами

| Формат | Метаданные и WCS | Точность | Сжатие | Ниша |
|---|---|---|---|---|
| **FITS** | Полные, стандарт | Без потерь | Tile-compressed | Архивы, наука |
| **TIFF** | Ограниченные | Без потерь | Да | Обработка изображений |
| **PNG / JPEG** | Нет / почти нет | PNG без потерь, JPEG с потерями | Да | Превью, визуализация |
| **HDF5** | Гибкие, но не стандарт астрономии | Без потерь | Да | Симуляции, большие кубы |
| **NumPy `.npy`** | Нет | Без потерь | Нет | Промежуточные массивы в пайплайне |

FITS выигрывает не скоростью и не размером, а **стандартизацией семантики**: любой архив и любой инструмент понимают его карточки одинаково.

## Частые ошибки

> [!danger]- 1. Чтение без контекстного менеджера
> Незакрытый `fits.open` держит файл и память (особенно при memmap).
> **Решение:** `with fits.open(...) as hdul:`.

> [!danger]- 2. Обращение к `hdul[0].data` в MEF-файле
> В MEF Primary HDU часто пустой: `data is None`.
> **Решение:** смотреть `hdul.info()` и брать данные из нужного расширения.

> [!danger]- 3. Доверие отсутствующим карточкам
> `BUNIT`, QC-флаги и WCS-карточки могут отсутствовать или быть некорректными.
> **Решение:** проверять наличие и документировать косвенные подтверждения единиц.

> [!danger]- 4. Запись поверх существующего файла без `overwrite=True`
> Astropy по умолчанию отказывается перезаписывать FITS.
> **Решение:** явно указывать `overwrite=True` либо писать в новые имена с версией.

> [!danger]- 5. Визуализация сырых значений без нормализации
> Динамический диапазон солнечных изображений огромен; линейная растяжка показывает «пустой» кадр.
> **Решение:** асин- или лог-растяжка при визуализации (это вопрос отображения, а не хранения).

## Вывод

> [!success] Итого
> **FITS** — контейнерный стандарт астрономических данных: последовательность HDU, каждая из которых pairing обязательного ASCII-заголовка и опциональных бинарных данных.
>
> Ключевые факты:
> - Заголовок — контракт: тип данных (`BITPIX`), размерности (`NAXISn`), единицы (`BUNIT`), время и инструмент, WCS.
> - Файл может содержать много расширений (MEF); Primary HDU часто пуст и несёт только общие метаданные.
> - Все блоки выровнены по 2880 байт.
> - **Tile-compressed FITS** хранит изображение как таблицу независимо сжатых плиток; базовый алгоритм **RICE_1** — адаптивное кодирование Голомба–Райса, обратимое для целых и управляемо-lossy для float через квантование.
> - Astropy читает и пишет такие файлы прозрачно (`CompImageHDU`).
>
> Для диплома: рабочая серия MDI — tile-compressed FITS с парой `continuum` (float32) + магнитограмма (float64); отсутствие `BUNIT`, QC-флаги `flat`/`dip` и epoch-дрейф порога umbra — задокументированные свойства архива, учтённые в пайплайне.
